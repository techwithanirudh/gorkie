## 2026-09-12

- **[Known issues]** Diagnosed why turns die silently, and fixed the cause in production. The reported symptom was a Slack thread that "stopped midway" with no reply for seven hours. It was not a hang and not a model problem. `gorkie-monitor.service` restarted the bot mid-turn, and because the app has no SIGTERM handler systemd SIGKILLed it 90 seconds later, destroying the in-flight turn and the buffered spans with it.

  Timeline, read off the production journal: `23:57:49` turn started; `00:02:01` `socket-mode:SlackWebSocket: A pong wasn't received from the server before the timeout of 5000ms!`, which is an independent subsystem reporting the event loop stalled past five seconds; `00:03:07` `health check failed (2/2)` and `systemctl restart`; ninety seconds of the app logging nothing at all; `00:04:37` `State 'stop-sigterm' timed out. Killing.`; `00:04:38` restart, online at `00:04:45`; zero turns between `00:05` and `00:30`.

  Why the loop stalled: the unit had `MemoryHigh=1G` and `MemoryCurrent` sat at `1073340416`, exactly on that line. `MemoryHigh` is a soft cap that makes the kernel continuously reclaim the cgroup's pages into swap, so the process was being swapped out by configuration, then blocking on major page faults to get its own memory back. The counter read 9,062,676 major faults and `/proc/pressure/io` showed `full avg10=42.81`, meaning everything on the box was fully stalled on disk 43% of the time.

  Three things turned out to be false and are worth recording. **Swap was never the constraint**: 5886 MB total with 4499 MB free, so adding swap would only have widened the target for eviction and made the thrashing worse. **The host never rebooted** (`uptime` 9 days) and the corpus-wide 134 minute quiet around the incident is ordinary, the corpus holds ten overnight gaps of 357 to 689 minutes. **The 406 watchdog restarts since 08-13 are not a steady rate**: 342 of them fall on 09-08 and 09-09, a crash loop firing every two minutes, which is a different failure from the healthy-but-stalled case. Steady state is one to four a day.

  Also corrected: adding `timeout` to the agents, which an earlier pass had ranked as the top fix for this, would not have prevented any of it. It guards a stalled provider, not SIGKILL from a watchdog. Still worth doing for the hang class it does cover, and it remains open in `TODO.md`.

- **[Known issues]** **This first attempt was wrong and caused an outage.** Raising `MemoryHigh` to `1400M` set it *equal to* `MemoryMax`, which deleted the reclaim buffer. The old config had `MemoryHigh=1G` against `MemoryMax=1400M`, so the kernel began reclaiming 400 MB before the hard wall: thrashy and slow, but survivable. With both at `1400M` the process grew freely to the hard limit where the only outcome is death, and at `15:42:13` the kernel OOM-killed it: `oom_memcg=/system.slice/gorkie.service`, `Killed process 509298 (bun)`, `anon-rss:1356348kB`, `Failed with result 'oom-kill'`. `Restart=always` brought it back and the in-flight turn was lost, the same user-visible symptom the whole exercise was meant to remove. Traded thrashing for OOM kills.

  Corrected to `MemoryHigh=1250M` with `MemoryMax=1550M`, restoring a 300 MB reclaim zone while still sitting well above the old 1 GB line. The lesson worth keeping: `MemoryHigh` and `MemoryMax` must never be equal. `High` is where the kernel starts working to keep you under; `Max` is where it gives up and kills. With no gap there is no "working to keep you under" phase at all.

  This also proved the footprint reduction is not optional. The process reached `memory.current` 1.47 GB and `memory.events` recorded `high 267382, max 408` before the kill, so it genuinely wants more than the box can give. Raising limits only moves the wall; `excludeSpanTypes` is what lowers the demand.

- **[Known issues]** Raised `MemoryHigh` from `1G` to `1400M` via `systemctl set-property gorkie.service MemoryHigh=1400M`, which applies to the live cgroup with no restart, so no turn was killed applying it. `/proc/pressure/io` went from `full avg10=42.81` to `full avg10=0.38` immediately, with `avg60=17.63` and `avg300=37.08` showing the decay from the old state. Resident swap stays where it was because pages already evicted are only faulted back when touched; what stopped is new eviction. Previous config backed up at `/root/memory.conf.bak.20260912`.

- **[Known issues]** Replaced the liveness monitor so it distinguishes busy from wedged. **Old implementation** (`/root/gorkie-monitor.sh.bak.20260912`): one `curl --max-time 8` against `127.0.0.1:4111` every 60 seconds, restart after `THRESHOLD=2` consecutive failures. That is a sampling test, not a duration test. With the process fully stalled 43% of the time, any single probe was close to a coin flip, and two unlucky samples a minute apart were enough to kill a turn that was working normally. The evidence it was too twitchy: 487 stalls recovered on their own against 406 that escalated.

  **New implementation**: five probes spread across roughly 24 seconds needing only two successes, cross-checked against `usage_usec` in `/sys/fs/cgroup/system.slice/gorkie.service/cpu.stat`. A wedged process burns no CPU; a thrashing but working one does. HTTP failing with CPU advancing means busy, so leave it alone; HTTP failing with CPU flat means wedged, so restart. `THRESHOLD=5` rounds, and `BACKSTOP=15` still catches a spin loop, which would keep CPU high while answering nothing.

  Chose the cgroup counter over the heartbeat file that was proposed first, and the reasoning matters: a heartbeat needs an app change and a deploy, it asks the process to self-report, and writing it requires the very event loop that is stalled. The cgroup counter is maintained by the kernel, needs no code change, and cannot be blocked by the thing it is measuring.

  Verified on the live box in both directions before installing. Healthy service: exit 0 in 24 seconds, service untouched. Six consecutive rounds of total HTTP failure with CPU advancing: zero restarts, logging "busy, not wedged: cpu advanced, leaving it alone". Five rounds with a faked frozen cgroup: restart fired correctly at the threshold.

- **[Architecture]** Set `excludeSpanTypes: [SpanType.PROCESSOR_RUN]` in `src/mastra/index.ts`. Committed to the repo only, not yet deployed. `deepClean` runs in the span **constructor** (`node_modules/@mastra/observability/dist/index.js:2897-2900`), deep-copying `input` and holding it on the span for the lifetime of the trace. `excludeSpanTypes` is checked in that same constructor and returns before any of it (`:2894-2896`), which Mastra's own comment on `isExcluded` describes as avoiding "both the deepClean cost and holding references to large payloads for the lifetime of the span".

  This reversed an earlier recommendation in `ISSUES.md` that preferred `customSpanFormatter` on the grounds that it keeps the spans and drops only the payload. That reasoning holds for storage and bandwidth and is wrong for memory: the formatter runs in `BaseExporter.exportTracingEvent` (`:4488-4526`) at export time, long after the constructor already spent the allocation. Memory is what was killing the bot, so the formatter was the wrong lever. Measured against 4337 traces, `processor_run` is 66.6% of span count, so this cuts memory, event-loop time, and billed events (about 126k a month becomes about 42k) together. The cost is losing per-processor latency data and the `stream-error-retry-processor` spans.

Approval is carried per tool via `needsApproval`, which Mastra reads off Vercel tools, and `GITHUB_WRITE_TOOLS` replaces the `readOnlyHint` sniffing, which also retires the `^(delete|remove)_` caveat below. `github_push_branch` brokers the credential at the sandbox firewall for one git command and requires approval unconditionally.
