### Summary

In Channels, a tool approval card posted for one user can be answered by **any** user who can see it. The approve/decline handler never checks who clicked, so a bystander in a shared channel can approve a write tool that was requested by someone else, and it runs under the original requester's turn.

### Where

`packages/core/src/channels/agent-channels.ts`. The approval record is stashed without any notion of who it belongs to:

```ts
const onApprovalPosted = (toolCallId, record) => {
  this.pendingApprovalCards.set(toolCallId, record);
};
```

and the action handler looks the record up by `toolCallId` alone, then proceeds. `_buildRenderContext(chatThread, platform, approvalContext)` has no requester parameter to thread one through, and `processChatMessage` has `message.author?.userId` available at the call site but does not pass it.

### Why it matters

Approval is the gate in front of destructive and credentialed tools. We use it for GitHub writes and for user-configured MCP servers, where the credential belongs to one specific person. In a shared Slack channel the card is visible to everyone in the thread, so today the gate authenticates nothing: it confirms that *somebody* clicked, not that the person who owns the action approved it. That turns a human-in-the-loop control into a UI speed bump, and it is the kind of thing that looks fine until the first time it is abused.

### Steps to reproduce

1. Configure an agent with Channels on Slack and a tool with `needsApproval: true`.
2. In a shared channel, have user A ask the agent to do something that triggers the tool.
3. Wait for the approval card.
4. Have user B, not A, click Approve.
5. The tool executes. Nothing distinguishes this from A approving.

### Expected

An approval action from a user other than the one whose turn requested it should be ignored, and ideally acknowledged to the clicker so it does not look broken.

### What we do locally

We patch `@mastra/core` with three hunks: add a `requesterId` parameter to `_buildRenderContext`, stamp it onto the record in `onApprovalPosted`, and bail out early in the action handler when the acting user does not match.

```ts
const approvalRequesterId = stashed?.requesterId;
const actingUserId = event.user?.userId;
if (approvalRequesterId && actingUserId && approvalRequesterId !== actingUserId) {
  this.log('info', `Ignoring tool approval action from ${actingUserId}: only ${approvalRequesterId} may answer toolCallId=${toolCallId}`);
  return;
}
```

The guard is deliberately permissive: it only rejects when both ids are known and differ, so anything that does not carry a requester behaves exactly as it does today. Happy to open a PR along these lines if the approach looks right. The open question we did not want to decide for you is whether a mismatched click should be silently ignored, as above, or get an ephemeral "this approval is not yours to answer" response, which is friendlier but platform-specific.
