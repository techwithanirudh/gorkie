## Backgrounding (design researched 2026-09-13, verified against @mastra/core@1.66.0 source)

Native Mastra background tasks (added 1.29.0) ARE installed and `@mastra/pg` ships the store, so they're adoptable. What they give gorkie: the tool's `execute` runs in-process on the host as an internal workflow, independent of the agent turn (dispatch, LLM finishes, turn ends, task keeps running), plus a durable Postgres task record (`mastra_background_tasks`), concurrency/retries/timeouts/suspend-resume, and `onTaskComplete`/`onTaskFailed` callbacks.

THE BLOCKER (verified): completion re-invokes the loop only via `agent.stream({ untilIdle })`, and gorkie never calls `agent.stream`, channels does. `untilIdle` appears NOWHERE in the channels dist (`node_modules/@mastra/core/dist/channels/`), and background-task completion emits no signal of its own. So a finished task silently writes its result to memory and nothing posts to Slack until the next user message. Patching channels to pass `untilIdle` is wrong: it holds the Slack run active (typing + Plan widget) for the whole job (default 5-min idle timeout between turns), defeating the point. AgentController (what Factory uses) also passes no `untilIdle`, so migrating buys nothing here.

THE FIX (no core change): bridge completion to gorkie's OWN existing signal-wake, the exact mechanism `wait.ts` already uses. Register `onTaskComplete`/`onTaskFailed` that call `orchestrator.sendSignal({ type: 'notification', ... }, { threadId, resourceId, ifIdle: { behavior: 'wake', streamOptions: { requestContext: { channel: ... } } } })`; the woken run's channels output processor rebuilds the Slack render context from the thread's persisted channel coords and posts. Factory does the same shape via SignalProviders (external event → notify → idle-wake).

What native tasks do NOT fix (irreducible custom work): the E2B keepalive. The dispatching turn still hits `processOutputResult -> pauseSandbox` at turn end (also `onAbort`/`onError`), freezing the box under the running task. Must (a) gate `pauseSandbox` on `backgroundTaskManager.listTasks({ threadId, status:'running' })` being empty so a thread with a live task keeps its box, (b) keep refreshing `e2b.setTimeout` from inside the long `execute` (current cap 16 min, `config.ts:5`), accepting the box stays running/billed, not paused, for the job, and (c) accept a host restart mid-build still loses the in-sandbox work (the task record survives; the executor closure and live E2B command do not).

BLOCKER FOUND 2026-09-13 (corrects the research's "mark the long sandbox tool background"): you CANNOT flip `execute_command` to background-eligible. Agent-level `AgentBackgroundToolConfig` is only `boolean | { enabled, timeoutMs }` (`node_modules/@mastra/core/dist/background-tasks/types.d.ts:176`), with NO `defaultDisposition`, and eligible tools default to `deferred`. Since channels never passes `untilIdle`, a deferred `execute_command` dispatches async and its result NEVER returns in-turn, breaking every command. `defaultDisposition: 'foreground'` exists only on the tool-level `ToolBackgroundConfig` (a `createTool`), which the Mastra-injected workspace `execute_command` can't set. So backgrounding needs a NEW gorkie-owned `createTool` (e.g. `run_background(command)`) with tool-level `background: { enabled: true, timeoutMs }` (deferred is correct for a dedicated bg tool the model calls only when it wants backgrounding); `execute_command` stays synchronous.

- [ ] Issue 35, proper background task tool, and the owner has now named the exact design to copy. The 8h comment on the issue pastes Claude Code's own pattern: a command that exceeds its timeout is not killed, it is *moved to the background* automatically with an id and an output file path, returned immediately, and the caller is notified when it completes (`Command did not complete within its 420s timeout and was moved to the background (ID: ...). Output is being written to: ...`). That is a better shape than what we shipped, which makes the model pre-declare `background: true` and silently loses a foreground command at the 15 minute cap. The target design: a foreground `execute_command` that hits its timeout should auto-convert to a background process rather than dying, hand back an id and a sandbox log path, and surface the result on a later turn. Timeout is required on the tool, per the issue. Note this composes with the fix already made (VM lifetime now exceeds the command cap, background processes survive via `abortSignal: false`), so the missing piece is the auto-convert-on-timeout and the completion notification, not the plumbing underneath. The notification path is the open question: channels wakes a thread on a new message, so a completed background job needs something to poke the thread, which is the same wake-path question the host-side `backgroundTasks`/`untilIdle` research raised. **Update 2026-09-13: durable completion notification done via prompt, not push.** `prompts/features/sandbox.ts` tells the model to chain `background: true` -> `wait` -> `get_process_output` -> report; `wait` uses Mastra's Postgres-backed schedules so it survives a restart, unlike an in-memory pid registry, and needs no onExit plumbing. Value is capped until pause-deferral, since `processOutputResult` still freezes the job between turns so it only advances during waking turns. Remaining, in order: (1) pause-deferral, skip the `processOutputResult` pause while a job is pending for the thread, needs only an in-memory pending-job flag with a safe fallback (lost flag -> pause as today), touches the live pause path; (2) auto-convert-on-timeout; (3) true push-on-exit, which needs a durable pid->thread map to survive the watchdog restarts, i.e. a Postgres job table = schema change, raise first. `onExit` meta carries only `{pid, toolCallId, exitCode, stdout, stderr}`, no thread/requestContext/schedules, which is why push needs the registry. **Mechanism confirmed 2026-09-12 by reading `workspace-Ds7WdjRA.js:8433-8520`, and it surfaces a real danger the owner flagged.** The background branch calls `sandbox.processes.spawn(command, { timeout: input.timeout ?? undefined, abortSignal })` and returns `Started background process (PID: n)` immediately, never `.wait()`ing, which is why it is not subject to the 15 minute foreground cap (that cap is the `.wait()` on the foreground path). Two things then remove every bound: `timeout` is `input.timeout ?? undefined`, so if the model omits it the process has **no timeout at all**, and we set `backgroundProcesses.abortSignal: false`, which the code resolves to `undefined` (`bgConfig.abortSignal || void 0`), so the turn-end abort no longer kills it either. The only thing bounding a no-timeout background process today is the accident that `processOutputResult` pauses the VM at turn end and freezes it; the moment we add the pause-deferral the auto-background design needs, that accidental cap disappears and a runaway `while true &` runs until the VM lifetime expires, burning the sandbox. So a cap is mandatory and must land in the same change as the keepalive: either make `timeout` required on the background branch (the issue says required) or enforce a max via `backgroundProcesses`, and keep the VM lifetime as the hard backstop. The cap should be larger than the 15 minute foreground cap, since the whole point of backgrounding is longer work, which means the VM lifetime and the keepalive re-arm have to stretch to match it (E2B allows up to 1 hour on Hobby, 24 on Pro), so the three numbers move together: background max timeout, VM lifetime, keepalive interval. How progress works meanwhile: a background process runs only while the VM is live, freezes on the turn-end pause, and resumes from the snapshot on the next sandbox command (`e2b start()` resumes "with background processes still running"), so it continues across turns but makes no progress between them. Mastra's agent loop never pauses the sandbox itself, so `processors/sandbox.ts` is not a duplicate, it is the only pause, which is why this is entirely our lever.
