## CRITICAL (2026-09-13)

- [x] **Live view video preview is a black screen; remove the Watch live button (2026-09-24).** Owner report: the card posts and the thumbnail shows, but the video block's player (the `/live/:ticket` page) stays black. Root cause: `src/mastra/server/live-view.ts` interpolated `${JSON.stringify(socket)}` inside `<script>` in a hono `html` template, and hono escapes every interpolation, so the served page read `new WebSocket(&quot;wss://...&amp;t=...&quot;)`: a syntax error, no script ran, and the dark body with no frame was all Slack showed. Confirmed by curling a freshly minted ticket's page from the running server. Fix: the URL goes in `<body data-socket="...">` (attribute escaping is decoded by the HTML parser) and the script reads `document.body.dataset.socket`; verified offline that the rendered script now parses. Ruled out with probes against the running `mastra start` (127.0.0.1:4111 and the quick tunnel): the WS route is registered (`/api/agents/orchestrator/browser/session` reports `screencastAvailable: true`; `@hono/node-ws` resolves from the repo root node_modules even though `.mastra/output/node_modules` lacks it), the tunnel upgrades WebSockets, a ticketed WS gets `{"status":"connected"}` locally and through the tunnel, and a proxied WS without a ticket is refused. Ticket thread id equals the browser session key (both come from `SandboxBrowser.connectThread`, and `slack.decodeThreadId` accepts it, which is why the card posts). Frame path not live-tested: no browser session was open during the probe. Also: `frame-ancestors` now lists `https://slack.com` (the apex is not matched by `*.slack.com`; `app.slack.com` is). Card (`src/mastra/chat/live-view.ts`): the Watch live `actions` block is gone; if `chat.postMessage` rejects the video block (its host must be in the app's unfurl_domains, which a new quick-tunnel host is not), the card is reposted with an `image` block of the same refreshing thumbnail, and refreshes keep that variant. The fallback card has no link to the live page, by design of the button removal. Needs a live test by the owner.
- [x] **Detailed tool display showed no task cards (2026-09-24).** Root cause: the per-run mode lost a race. `ChatChannelOutputProcessor` (`node_modules/@mastra/core/dist/agent-DwtTO5Px.js:21427`, `processDataParts = true`) opens its driver on the first chunk it sees and copies `render.toolDisplay` into `runStreamingDriver` then (`:21494-21498`; `groupTasks` is fixed at `:20784`). Observational Memory writes `data-om-status` from `processInputStep` on every step (`@mastra/memory` `src-zTE4189S.js:29482`, via `emitProgress` at `:30725`), before the model streams, and that part goes through the output processors (`agent-DwtTO5Px.js:29468`). Our `tool-display` processor had no `processDataParts`, so Mastra skipped it for data parts (`:4736`) and the render processor opened with the adapter default `hidden`; the later rewrite to `timeline` changed nothing. Fix in `src/mastra/processors/tool-display.ts`: `processDataParts: true`, and the lookup is memoised as a promise on `state` that every chunk awaits, because OM also writes some parts without awaiting (`src-zTE4189S.js:27190` and others). Ruled out: settings persistence (`setToolDisplay`/`getToolDisplay` both key on `rawId`), processor order (configured processors run before channel ones, `agent-DwtTO5Px.js:35641-35645`), recipient context for native streaming in channel threads (Chat SDK fills `recipientUserId`/`recipientTeamId` from the current message, `chat` `Thread.handleStream`). No patch needed. Needs a live test by the owner.
